# ReviewDebt: a practical framework for scoring every pull request — Sachin Gupta, Ebay

## Summary
Sachin Gupta, a software engineer at eBay, does not claim coding agents are bad or slow. He claims they create a debt "that nobody is measuring." Review debt is the gap between code an agent produced and code humans have reviewed, trusted and understood. It compounds like financial debt, and the interest is paid in human attention.

**The evidence for the gap**
GitHub's October 2025 report shows commits up 25% year over year while review comments fell 27%. Faros AI's 2026 benchmark shows median PR review time up 441.5% and 31% more PRs merged with no review. He calls the headline gains (PRs per developer up 16%, median PR size from 44 to 72 lines, cycle time modestly down) vanity metrics: they measure "the speed of production," not "the speed of trust." The hidden costs are reviewer fatigue, late-night merges, test theater, architectural drift and incident lag.

**Why it compounds**
Three feedback loops: unreviewed code grounds the agent's next PRs, reviewers stop making architectural calls and check only syntax, and leadership resets velocity expectations without hiring more reviewers.

**Five deterministic signal families**
Ten checks, all computable from a PR and its repo, with no language model. An LLM judge would make the score drift with model changes and would not survive an engineering review.
- **Diff size and coupling.** Agents fix at the call site and sprawl across files. Humans route fixes to the root cause.
- **Test evidence gap.** Test lines over production lines. Agent tests often assert what the code does, not what it should do, and lock in bugs.
- **Directory and ownership spread.** Distinct code-owner teams touched. Three hours of saved typing gets spent as multi-party review.
- **AI authorship indicators.** Co-authored footers, branch prefixes, "generated by" phrases. These flag PRs for attention, not blame.
- **Evidence and rationale gaps.** Does the PR explain the why? He contrasts an 18-character body with a commit message reading "updates" against one with symptom, diagnosis, change and benchmark link.

**The score and three examples**
Signals combine into one 0-100 number, banded at 0-24 low, 25-49 normal, 50-74 needs author evidence before senior review, and 75+ split or request context. A clean PR scores 0 with six estimated minutes and an almost empty report. A high-debt PR scores 60 with 86 minutes, and the AI indicator supplies only five of those points. A well-shaped AI PR with tests scores 7. The output lists what fired, where the reviewer should focus and what the author should do next.

**The 524-PR scan**
Across three unnamed public repos, AI authorship stayed flat at 5 to 20%, but review burden climbed with volume. One repo accrued 186 senior reviewer hours in 27 days, another 43. The four PRs in high bands were all structural changes: migrations, SDK rewrites, multi-team refactors. One PR alone was estimated at 5,036 minutes.

**What to do**
One logical change per PR, tests that assert intended behavior, one owner territory, the human writes the why, and the same review standard for AI PRs. Adoption: backfill the last 200 merged PRs, set a threshold such as 50, post scores as non-blocking comments, aggregate weekly per team, and discuss the slope in retrospectives.

## Why it matters
- It gives a name and a number to a cost that throughput dashboards hide, with cited industry data showing output rising while review attention falls.
- The insistence on deterministic checks over an LLM judge is a clear argument for metrics that stay stable across model versions and can be defended to leadership.
- The 524-PR scan supports a nuanced claim for any coding-agents chapter: AI authorship does not drive review burden by itself; volume and PR shape do.
- The concrete PR hygiene rules and the five-step rollout (backfill, threshold, surface, aggregate, discuss) are directly usable by teams adopting agents.
